# Host、客户端与服务端：MCP 的进程拓扑

> Host 从不直接与服务端通信，而是为每个服务端配备一个客户端。MCP 正是在这一对一绑定处划定信任边界；当 host 聚合多个服务端时，也必须从这里开始解决名称冲突。

**类型：** Reference
**语言：** Python
**前置要求：** 第 05 课
**预计时间：** 约 45 分钟

## 学习目标

- 说出 MCP 系统中的三个参与者——host、客户端和服务端——以及各自职责
- 解释为什么 host 会为每条服务端连接嵌入一个独立客户端，而不是让一个客户端同时应付多个服务端
- 区分本地 stdio 服务端和远程 Streamable HTTP 服务端，并解释各自的信任沿哪条边界划分
- 将服务端原语 tools、resources、prompts、completion 以及各项客户端功能，与其控制方或提供方一一对应
- 将多个已连接服务端的工具聚合到同一个注册表，用服务端 id 前缀解决名称冲突，并解释为什么绝不能使用服务端自报的 `serverInfo.name` 作为路由键

## 问题背景

设想一个助手同时连接三个系统：文件服务端、笔记服务端和指标服务。每条连接都使用你在无状态核心和时代协商课程中学过的无状态请求形状：每个请求都写入自己的协议版本和能力，调用之间不保留任何连接状态。但前几课没有回答另一个问题：host 同时与三个服务端通信时，究竟是谁在和谁说话？如果两个服务端给自己起了相同名称，或暴露了同名工具，又该怎么办？

一种简单粗暴的设计会把三个服务端压进同一个繁忙的连接对象，再由它记录每条消息来自哪里。这种设计无法清楚表达结果来自哪个服务端，无法阻止某个服务端声明的能力泄漏到另一个服务端的调用中；而且当两个服务端碰巧都在自我描述中把自己称为“primary”时，它也无法区分二者。这绝非边缘情况。任何连接多个 MCP 服务端的 host 都必须解决它。规范没有依靠开发者自律，而是用结构解决问题：固定角色、每组配对一条连接，以及处理彼此毫不知情的独立服务端发生命名冲突的规则。

## 核心概念

MCP 系统由三个参与者组成，每个角色的职责都很明确。**Host** 是用户实际运行的单一应用进程，例如聊天助手、IDE 或批处理流水线。Host 创建客户端，控制允许建立哪些连接，在工具运行前执行同意检查，并聚合各个已连接服务端返回的上下文。系统中只有 host 能看到所有服务端拼成的全貌。

**客户端**是 host 创建的对象，在一条连接的整个生命周期内，每个客户端只对应一个服务端。这不是建议，而是架构用来阻止不同服务端相互渗透的方式。Host 需要连接第二个服务端时，不会复用第一个客户端的连接，而是创建第二个客户端。拥有三个活跃服务端的 host 就有三个客户端对象：每个对象连接自己的服务端，在每个请求中写入你在无状态核心中见过的协议版本与能力，而且永远看不到另外两个客户端的活动。客户端还承担一些不会泄漏到线协议中的记账工作：关联请求 id、跟踪服务端声明的能力，以及记住自己有权向哪个服务端发起工具调用。

**服务端**是独立程序，可以是**本地**服务端，也可以是**远程**服务端。本地服务端通常作为子进程启动，通过 stdio 通信；消息是以换行分隔、没有标头层的 JSON-RPC，因此全部内容都放在 `_meta` 中。远程服务端通常是通过 Streamable HTTP 访问的长驻服务，每条消息使用一个 POST；除了 `_meta` 中的版本，还必须在标头中重复协议版本。信任沿服务端实际跨越的边界划分。本地 stdio 服务端跨越进程边界：它通常以同一用户身份运行，直接从环境读取凭据，而且规范指出 stdio 实现不应执行 OAuth 流程。远程 Streamable HTTP 服务端跨越网络边界：它通常由另一个团队或公司运营，授权框架也是为这种传输设计的，包括 bearer token、受保护资源元数据和 audience 验证。两种边界没有谁天然更安全；它们只是不同。Host 应按每个已连接服务端实际跨越的边界判断风险，而不能把所有“服务端”视为同一类对象。

规范还提出了一条值得牢记的设计原则：服务端不应读取完整对话，也不应看到其他服务端的内容。客户端发送的每个请求只携带本次请求所需的信息，而不是 host 的完整历史。两个已连接服务端之间的隔离并非礼貌约定，而是由架构强制保证：它们是不同进程，与互不交换信息的不同客户端对象通信。

服务端原语按控制方划分。**Tools** 由模型控制：模型根据工具的名称、描述和输入 schema 决定何时调用。**Resources** 由应用驱动：host 决定获取哪些资源并将其放入上下文，资源本身只是 URI 和内容。**Prompts** 由用户控制：人会明确选择模板，而不是让模型自行取用。第四项服务端功能 **completion** 为 prompt 或资源模板的参数提供自动补全；它也跟随应用，因为由 host 决定在用户输入时给出哪些建议。客户端功能的方向相反，由服务端向客户端索取内容。**Elicitation** 允许服务端在调用途中向用户请求信息；它以 `input_required` 结果送达，客户端通过带有 `inputResponses` 的重试回答，在当前修订版中仍处于 Active 状态。**Sampling** 和 **roots** 自 2026-07-28 起都已弃用：sampling 曾允许服务端请求客户端代为运行模型补全，新服务端应直接调用 LLM 提供商 API；roots 曾允许客户端公布文件系统边界，新服务端应改为通过工具参数、资源 URI 或服务端配置接收目录。Deprecated 不代表 Removed。两者仍可工作，最早也只能在 2027-07-28 当天或之后发布的修订版中移除。

把多个服务端放在同一个 host 后面，聚合问题就出现了。工具名称只需在单个服务端内保持唯一。两个从未互相知晓的服务端完全可能都暴露名为 `search` 的工具，也可能在 `server/discover` 结果中报告相同的 `serverInfo.name`，因为该字段由服务端运营者自行填写。如果 host 使用服务端自报名称作为聚合注册表的键，或让第二个 `search` 静默覆盖第一个，就可能在无人察觉时把模型的工具调用路由到错误服务端。解决方案分两步。第一，注册表中的每个条目和每次路由判断都必须使用 host 建立连接时自行分配的连接标识，例如配置键或槽位索引；它必须由 host 控制，绝不能使用 `serverInfo.name`。第二，两个服务端声明同名工具时，保留第一个工具的普通规范名称，并给后续冲突项加上服务端 id 前缀，让两个工具都以不同名称保持可达。无论 host 如何聚合，工具所属服务端仍会执行自己的错误规则：未知工具仍返回 `-32602`，错误参数仍作为工具执行错误返回，与聚合前完全相同。

## 交互实验

图中，一个 host 进程内有三个客户端方框，每个方框分别连接右侧自己的服务端。Files 和 notes 被画为使用 stdio 传输的本地服务端，并且有意让两者都把 `serverInfo.name` 自报为“primary”。Metrics 被画为使用 Streamable HTTP 的远程服务端，它只声明 resources 能力，没有 tools。观察图的底部：注册表让 `search` 继续指向最先声明它的 files，并将 notes 中冲突的 `search` 暴露为 `notes/search`。有一个名称从未出现在注册表中：files 和 notes 共用的自报名称“primary”。Host 在决定如何路由时，根本不会先问服务端如何称呼自己。

## 实践实验

打开 `code/main.py`。它只使用标准库构建三个服务端，不访问网络，也不依赖 SDK，但消息形状严格遵循 2026-07-28 schema。`build_host()` 使用三个独立的 `Client` 对象将 `Host` 分别连接到 `files`、`notes` 和 `metrics`，每个服务端对应一个客户端，然后调用 `build_registry()` 聚合它们的工具。

```bash
python3 code/main.py
```

对照上面的概念部分阅读输出。第一块会并列显示每条连接由 host 分配的 id 与服务端自报名称：files 和 notes 都报告“primary”，证明自报身份不能用作安全的键。第二块展示聚合注册表：`search` 映射到 files，`notes/search` 映射到 notes；注册表中没有任何条目指向 metrics，因为 metrics 从未声明 `tools` 能力，host 也从未向它发送 `tools/list` 请求。后续逐客户端交互展示每个请求的 `_meta` 块和每个结果的 `resultType`。最后两项分别是：一次缺少参数的路由调用返回 `isError: true`；一次直接调用 notes 服务端并指定其不存在的工具，返回 JSON-RPC 错误 `-32602`。这两项都符合前面课程所述的双错误通道规则。

接着修改内容并重新运行。可以添加第四个服务端，让它的 `serverInfo.name` 也与“primary”冲突，但使用新的 host 分配 id，然后确认注册表仍能按 id 正确路由。也可以让 files 和 notes 再出现一个工具名称冲突，确认前缀规则会再次生效，而且不需要修改 `Host.route`。

## 关键术语

| 术语 | 含义 |
|------|------|
| Host | 用户运行的单一应用进程；负责创建和管理客户端 |
| 客户端 | Host 创建的对象，在连接的整个生命周期内只绑定一个服务端 |
| 服务端 | 暴露 tools、resources 和 prompts 的独立程序，可以是本地（stdio）或远程（Streamable HTTP）服务端 |
| 本地服务端 | 通过 stdio 访问的子进程；信任沿进程边界划分 |
| 远程服务端 | 通过 Streamable HTTP 访问的服务；信任沿网络边界划分 |
| 控制模型 | Tools 由模型控制，resources 由应用驱动，prompts 由用户控制 |
| Elicitation | 允许服务端通过一次 MRTR 往返向用户请求输入的客户端功能 |
| serverInfo.name | 服务端自报身份，只用于显示和日志，绝不能作为路由键 |
| 服务端 id 前缀 | Host 为冲突工具名添加的消歧前缀，例如 `notes/search` |
