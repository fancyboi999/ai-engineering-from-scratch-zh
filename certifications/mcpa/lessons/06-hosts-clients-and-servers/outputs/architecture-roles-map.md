# 架构角色图

面向 MCPA「Architecture and Components」领域、与 MCP 2026-07-28 对齐的一页式参考资料。

## 三个参与者

| 角色 | 定义 | 职责 |
|------|------|------|
| Host | 用户工作的应用进程（聊天助手、IDE 或批处理流水线） | 创建和管理客户端、执行安全与同意检查、聚合多个服务端的上下文、协调模型 |
| 客户端 | Host 创建的对象，每条服务端连接对应一个 | 为每个请求附加协议版本和能力，隔离不同服务端的数据 |
| 服务端 | 暴露上下文和能力的独立程序 | 实现 tools、resources、prompts 和 completion；声明自身能力；永远看不到完整对话 |

牢记这条规则：一个客户端、一条连接、一个服务端。Host 连接五个服务端时会运行五个客户端，绝不会让一个客户端同时应付五段对话。

## 本地与远程服务端

| | 本地服务端 | 远程服务端 |
|---|---|---|
| 传输 | stdio（子进程、以换行分隔的 JSON-RPC） | Streamable HTTP（每条消息一个 POST，可选 SSE） |
| 承载信任的边界 | 同一台机器上的进程边界 | 独立 origin 的网络边界 |
| 典型客户端数量 | 通常在进程生命周期内只有一个客户端 | 多个 host 实例往往会产生多个客户端 |
| 凭据 | 从环境读取；stdio 实现不应执行 OAuth 流程 | 推荐使用 OAuth 2.1 流程取得的 bearer token |

## 服务端功能与客户端功能

| 功能 | 所属方 | 控制方 | 2026-07-28 状态 |
|---|---|---|---|
| Tools | 服务端 | 模型 | Active |
| Resources | 服务端 | 应用 | Active |
| Prompts | 服务端 | 用户 | Active |
| Completion | 服务端 | 应用（参数自动补全） | Active |
| Elicitation | 客户端 | 用户，通过 MRTR 往返完成 | Active |
| Sampling | 客户端 | 用户批准，客户端居中协调 | Deprecated，应迁移为直接调用 LLM 提供商 API |
| Roots | 客户端 | Host，仅提供建议性边界 | Deprecated，应迁移为工具参数、资源 URI 或服务端配置 |

## 多服务端 host 聚合检查清单

1. 使用 `server/discover` 分别发现每个已连接服务端；绝不要假设某个服务端的能力也适用于另一个。
2. 只有服务端确实声明 `tools` 能力时，才通过 `tools/list` 将其加入工具注册表。
3. 注册表中的每个条目和每次路由决策，都使用 host 建立连接时自行分配的连接标识，例如配置键或槽位索引。绝不要使用 `serverInfo.name`：它由服务端自行报告，两个独立服务端可能使用相同名称。
4. 工具名称在单个服务端内保持唯一，但不同服务端之间可能冲突。出现冲突时，保留第一个服务端的普通名称作为规范条目，并将后续冲突项暴露为 `<server-id>/<tool-name>`。
5. 路由调用时，先查找注册表条目，再把 `tools/call` 发送给拥有该工具的唯一连接。无论 host 如何聚合，接收请求的服务端仍会执行自己的错误规则（未知工具返回 `-32602`，错误参数返回工具执行错误）。
6. 将每个服务端的 tools、resources 和 prompts 与其他服务端隔离。只有 host 能横跨所有服务端查看信息。

## 考试要点

- Host 为每个服务端嵌入一个客户端；一个客户端绝不服务两个服务端。
- Tools 由模型控制，resources 由应用驱动，prompts 由用户控制。
- Sampling 和 roots 在 2026-07-28 中是 Deprecated，而不是 Removed；两者仍可正常工作。
- `serverInfo.name` 仅用于显示和日志，绝不能用于身份识别或路由。
