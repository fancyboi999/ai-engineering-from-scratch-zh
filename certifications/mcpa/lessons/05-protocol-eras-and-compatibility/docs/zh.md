# 区分现代 MCP 服务端与旧版服务端

> 现代 MCP 不再使用连接握手。因此，要同时兼容当前和旧版服务端，客户端必须根据第一次交互的实际表现判断对方属于哪个时代，而不能指望任一方预先声明。

**类型：** Reference
**语言：** Python
**前置要求：** 第 04 课
**预计时间：** 约 45 分钟

## 学习目标

- 说出从 2024-11-05 到 2026-07-28 的修订时间线，以及每个修订版的主要变化
- 定义现代、旧版和双时代，并读懂各种客户端时代与服务端时代组合的兼容性矩阵
- 在 stdio 上使用 `server/discover` 探测服务端，并在不依赖某个特定错误码的前提下，将响应分类为现代、版本不同的现代或旧版
- 解释客户端如何在收到 `UnsupportedProtocolVersionError`（错误码 -32022）后协商版本，而不执行握手
- 说明 2026-07-28 彻底移除了哪些内容，以及为什么只支持现代版本的服务端在拒绝旧连接尝试时仍应列出自己支持的版本

## 问题背景

现实部署不会同时完成升级。今天构建的客户端库，仍要与数月乃至数年前编写的服务端通信：有些在新修订版发布当天便完成更新，有些则自安装后从未改动。2026-07-28 修订版移除了早期版本用来处理这种差异的机制：在实际工作开始前，通过一次连接开场交互声明版本。如今每个现代请求都能自我描述，协议也因此实现了无状态，但客户端和服务端不再有专门的时刻来约定基本规则。

因此，要覆盖如此跨度的服务端，客户端在真正发挥作用之前必须先解决一个问题：面对一条尚且一无所知的连接，如何低成本且可靠地判断另一端会读取现代的逐请求元数据，还是仍在等待旧式问候。猜错之后，交互会以令人困惑的方式失败：现代服务端看到不认识的方法，或旧版服务端尝试解释一个缺少其预期信息的请求。本课要按照规范有意识地做出判断，而不是靠偶然试对。

## 核心概念

下表列出协议所有具名修订版及其标志性变化。只有最新版本属于现代时代，其余都属于旧版时代。

| 修订版 | 时代 | 主要变化 |
|---|---|---|
| 2024-11-05 | 旧版 | 首个公开修订版：提供 stdio 和 HTTP+SSE 传输，以及每次连接开始时执行的握手。 |
| 2025-03-26 | 旧版 | Streamable HTTP 取代 HTTP+SSE；加入 OAuth 2.1 授权、工具注解和音频内容。 |
| 2025-06-18 | 旧版 | 加入结构化工具输出、资源链接、elicitation、OAuth 资源服务端分类和 MCP-Protocol-Version 标头；移除 JSON-RPC 批处理。 |
| 2025-11-25 | 旧版 | 加入图标、增量 scope 同意、工具命名指导、URL 模式 elicitation 和实验性 task；验证错误改为工具执行错误，而非协议错误。 |
| 2026-07-28 | 现代 | 采用无状态核心，取消握手和会话；加入 `server/discover`、Multi Round-Trip Requests、`resultType` 和 `subscriptions/listen`；将 task 移至扩展；弃用 roots、sampling、logging 和 Dynamic Client Registration。 |

三个词贯穿本课余下内容。**现代**指版本、身份和能力通过逐请求元数据传递的修订版，即 2026-07-28 及后续版本。**旧版**指通过 `initialize` 握手打开连接并为会话保存状态的修订版，即 2025-11-25 及之前的版本。**双时代**指同时支持两者的客户端或服务端实现；它必须先明确判断对方所属时代，再解析其他内容。

双时代客户端的全部工作可以归结为一次探测。在 stdio 上，它会在发送任何实际请求前，先发送一个在 `_meta` 中携带首选版本的 `server/discover`，然后读取返回内容：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32022,
    "message": "Unsupported protocol version",
    "data": {
      "supported": ["2026-07-28", "2025-11-25"],
      "requested": "1900-01-01"
    }
  }
}
```

三种结果对应三种结论。收到 `DiscoverResult`，说明服务端是现代服务端：从其 `supportedVersions` 中选择一个版本并继续。收到可识别的现代错误——上例是 `UnsupportedProtocolVersionError`——仍说明服务端属于现代时代，只是并不支持客户端首次尝试的版本：改用 `data.supported` 中列出的版本和新的请求 id 重试，不要因此放弃现代路径。其他任何结果，包括客户端无法识别为少数几种现代错误形状的错误，或在合理超时时间内完全没有响应，都说明服务端属于旧版：回退到旧版 `initialize` 握手。第三种情况尤其重要。回退绝不能绑定某个特定错误码，因为旧版服务端没有义务始终以同一种方式响应陌生方法；它可能返回 Method not found、Invalid params，也可能一直挂起。判定“旧版”的依据是没有收到可识别的现代响应，而不是收到了某个特定错误。

在 Streamable HTTP 传输上，同一思路有不同形式，因为现代服务端也会因多种常见原因返回 `400 Bad Request`：版本不受支持、缺少能力，或标头与正文不一致。双时代客户端先尝试发送现代请求，收到 400 后必须先读取响应正文，再作判断。正文中可识别的现代 JSON-RPC 错误仍然代表现代服务端，因此客户端应修正请求或改用支持的版本重试，而不是回退。正文为空，或无法解析为可识别的现代错误，则说明服务端属于旧版；客户端应回退到旧版握手，必要时还要进一步回退到早于 Streamable HTTP 的已弃用传输方式。

时代是服务端的属性，不是单个请求的属性。因此，客户端应在 stdio 连接进程的生命周期内缓存判断结果，或按 HTTP origin 缓存，也可以在相同配置重启后继续保留这一判断。如果缓存假设后来失效，例如服务端已升级，客户端可以重新探测，无须永远相信过期结论。

还有一条规则值得掌握，因为它保护的是最难自行恢复的用户：即使服务端只支持现代版本，在响应 `initialize` 请求时返回的任何错误中，也应列出自己支持的版本。旧版客户端自身无法向前切换，它能向用户展示的诊断信息只有服务端在这条消息中提供的内容。

2026-07-28 移除的是整套旧版开场流程，而不只是缩减它。`initialize` 请求和随后发送的 `notifications/initialized` 通知均已消失。协议会话、标识会话的标头、独立 GET 流及配套的会话销毁流程也一并移除；两个资源监听方法则由 `subscriptions/listen` 取代。一些会话级方法失去了存在位置，按事件 id 恢复数据流的能力也已消失；除回复客户端发来的内容外，服务端不能再主动向客户端寻址。任何声称属于现代时代的交互记录都不应出现这些内容；如果兼容性示例确实需要展示，必须明确标注其旧版身份。

## 交互实验

图中展示一次探测的三种结局：`DiscoverResult` 方框直接指向“使用该版本”；可识别的 `-32022` 方框指向“使用受支持版本重试”；“其他错误或超时”方框则指向回退。注意，三种结果中有两种仍然属于现代时代。只有第三种会改变客户端接下来发送的消息类型。

## 实践实验

打开 `code/main.py`。`LEGACY_EXAMPLES` 被设为 `True`，因为本课确实需要构造旧式开场交互：一是展示双时代客户端如何回退，二是展示现代服务端如何拒绝旧请求并列出自己的版本。交互记录中的每条此类消息都包装为 `{"legacy": true, "message": {...}}`；文件内其他消息均为普通现代请求或结果，绝不会使用该包装。

```bash
python3 code/main.py
```

演示会构建四个服务端，并让同一个 `DualEraClient` 探测它们。`modern-server` 只支持 `2026-07-28`，所以第一次探测立即返回 `DiscoverResult`。`modern-other-version-server` 是专为实验虚构的第二个现代服务端，它固定使用一个编造的更晚版本，以便你观察重试路径：首次探测返回 `-32022`，客户端随即使用 `data.supported` 中列出的版本自动重试，全程不会进入回退路径。`legacy-error-server` 收到无法识别的方法后返回普通的 Method not found 错误，客户端会正确判定它属于旧版；`legacy-timeout-server` 则完全不响应探测，客户端同样将其判定为旧版，由此证明回退并不依赖某个特定错误。再次探测 `modern-server`，比较前后的日志长度：由于时代信息已经缓存，不会再发送新消息。最后，观察 `modern-only-server` 如何拒绝旧式开场请求，同时在错误中列出自己支持的版本——现代专用服务端就该这样做。

第 33 课综合项目中的交互完全使用现代术语，其中没有任何探测。这样做之所以安全，正是因为有本课作为前提：在那次交互的上游，客户端已经执行了本课教授的探测，并确认可以把连接当作现代连接处理。有人要求解释设计为何能跳过时代检测时，答案应是本课所述的前置探测，而不是未经验证的假设。

## 关键术语

| 术语 | 含义 |
|------|------|
| 现代 | 2026-07-28 或之后的修订版，版本和能力通过逐请求元数据传递 |
| 旧版 | 2025-11-25 或之前的修订版，通过握手打开连接并维持会话 |
| 双时代 | 同时支持两个时代，并在解析任何内容前明确判断时代的实现 |
| `initialize`（旧版） | 2026-07-28 之前用于打开旧版连接的握手；现代时代已移除 |
| `server/discover` | 双时代客户端在 stdio 上探测服务端时代所用的请求 |
| `DiscoverResult` | 将服务端标识为现代服务端并列出其支持版本的响应 |
| UnsupportedProtocolVersionError | 错误码 -32022；可识别的现代错误，只会触发重试，绝不触发回退 |
| 时代缓存 | 按服务端进程或 origin 保存探测结论，而不是每个请求都重新探测 |
| 兼容性矩阵 | 展示客户端时代与服务端时代所有组合结果的表格 |
| 检查 400 正文 | 在 HTTP 上，先检查 400 响应正文中是否存在可识别的现代错误，再判断是否为旧版 |
| 现代专用服务端的拒绝响应 | 现代专用服务端拒绝旧式开场请求时，列出自己支持的版本 |
