# MCP 工具调用的风险与安全控制

> 工具描述并不是恰好会被模型看到的文档，而是模型当作指令读取的字符串。因此，它也是攻击一个看似严密封锁的系统时成本最低的入口。

**类型：** Reference
**语言：** Python
**前置要求：** 第 25 课
**预计时间：** 约 45 分钟

## 学习目标

- 列举一个授权正确、无状态的 2026-07-28 部署仍会暴露的攻击面：元数据投毒、rug pull、工具遮蔽、混淆代理、token 透传、`requestState` 篡改、SSRF、DNS 重绑定、恶意图标和供应链漂移
- 用哈希固定工具定义，并在后续描述符相对先前批准版本发生变化时立即发现
- 把工具的描述、注解和结果视为模型会当作指令读取的不可信输入，而不是已经由人审核过的文档
- 阻止 token 透传，避免限定给 MCP 服务器的凭据流向无关的上游 API
- 当调用因策略而非请求格式错误被拒绝时，使用带 `isError` 的工具执行结果，而不是杜撰协议错误码

## 问题背景

某个支持网关聚合了十几台 MCP 服务器，让一个助手可以搜索工单、读取内部文档，并把已解决的案例推送到计费系统。从模型的角度看，这些服务器都只是文本：名称、描述、schema，以及工具调用返回的内容。协议不会判断这些文本是否诚实，只会判断消息格式是否正确。而一条消息完全可以格式正确，同时对工具的实际行为撒谎。

第 22 课划出了信任边界，第 25 课构建了同意门，在破坏性调用执行前要求人工确认。但二者都无法单独解决全部问题。同意机制只拦截人实际看到的调用；对于模型早已读过、并据此决定调用哪个工具的描述，它无能为力，也管不到那些没人逐一审核的日常非破坏性调用。网关需要一套无人值守时依然有效的控制，而且要在问题进入确认对话框之前就将其捕获。

## 核心概念

安全与治理需要分层构建。第 22 课定义了信任区；第 23、24 课说明客户端如何证明身份；第 25 课实现了由人批准某次具体调用的环节。本课讲的是这些机制的底层：服务器或网关如何自动处理那些无人逐一审核的调用，以及在人看到任何内容之前，如何应对已经进入模型上下文的工具描述。

工具的名称、描述、注解、图标和结果都应视为模型的不可信输入，就像第 22 课对待服务器提供的其他内容一样。描述里可以嵌入与工具实际功能毫无关系的指令，例如要求模型再调用另一个工具、把输出转发到别处，或向用户隐瞒某个步骤。模型把自然语言当自然语言读取，无法仅凭语气分辨真实的使用说明和攻击，因此“更仔细地阅读”不是防御手段。工具返回值也有同样的风险。一个成功且格式规范的 `CallToolResult`，可信度只取决于生成它的服务器。遭入侵或恶意的服务器既可以把指令藏进描述，也能轻易藏进正常结果的文本内容。静态扫描器可以在注册时和每次变更时检查诸如“忽略先前指令”或“不要向用户透露此步骤”等措辞，成本很低。但它只是绊线，不是安全证明：措辞足够隐晦时可能漏报，合法警告碰巧使用相似措辞时也可能误报。命中后应交给审核者判断，而不是自动裁决。

昨天通过审核的工具不会永远保持不变。rug pull 指已批准工具的名称、描述、schema 或注解发生变化。危险之处在于名称通常不变，因此后续调用表面上没有任何异常。只固定描述文本会漏掉 schema 或注解变化，而这些变化同样可能改变工具能力。因此要固定完整描述符：先规范化，再计算哈希。

```python
payload = json.dumps(
    {"name": name, "description": description, "inputSchema": input_schema},
    sort_keys=True, separators=(",", ":"),
)
digest = hashlib.sha256(payload.encode("utf-8")).hexdigest()
```

把摘要与工具的限定名称关联存储。每次刷新时，未知键要等待审核；重复的非限定名称需要加命名空间；已知键的摘要一旦改变，就是 rug pull：隔离工具、等待复审，只有确实有人检查后才纳入新摘要。哈希相同只能证明定义稳定，不能证明安全。一份被投毒的描述符即便固定得再牢，仍然是有毒的。因此，固定定义只是叠加在描述扫描之上的变更检测器，绝不能替代扫描。

两台互不知情的服务器可能都暴露一个名为 `search` 的工具。聚合网关若让发现顺序悄悄决定胜者，就造成了工具遮蔽：本该发往一台服务器的 `search` 调用可能被路由到另一台，而请求本身看不出错误。第 06 课正因如此，已经用服务器标识符为聚合后的名称加前缀；第 09 课的清单审核也会单独标记未限定、容易冲突的名称。批准、审计、哈希固定和路由都应引用限定名称，而不是描述或服务器自行报告的 `serverInfo`。

代表客户端调用第三方 API 的 MCP 服务器本身也是 OAuth 客户端，因此它是一个代理：使用他人委托的权限行事。混淆代理攻击会诱使这个代理替攻击者使用自身权限，最常见的场景是静态 client id 配合浏览器中早先合法流程留下的同意 cookie。更日常、更常见的同类错误要简单得多：token 透传。处理器把客户端用于向 MCP 服务器认证的 bearer token 原样转发给无关的上游 API。

```json
{
  "http": {"headers": {"Authorization": "Bearer client-bearer-9f2c"}},
  "message": {
    "jsonrpc": "2.0", "id": 5, "method": "tools/call",
    "params": {
      "name": "sync_upstream_ticket",
      "arguments": {"ticket_id": "T-88", "upstream_credential": "client-bearer-9f2c"}
    }
  }
}
```

`arguments.upstream_credential` 的值与入站 bearer token 完全相同。处理器若将其转发，就等于把只针对 MCP 服务器自身受众验证过的凭据交给了上游 API。解决办法不是更聪明的解析，而是拒绝转发，改为签发单独限定给上游的凭据。授权安全注意事项对此有明确要求：服务器必须验证 token 是否为自身受众签发，也绝不能把从客户端收到的 token 透传给上游。

第 14 课深入讲解了多轮往返请求，但其中的 `requestState` 字段也必须列入本课的威胁清单，因为它离开服务器后就由攻击者控制。不能相信客户端会原样返回。如果 `requestState` 会影响授权决策、资源访问或业务逻辑，就要对其签名或加密，将其绑定到已认证主体、较短的有效期和所属请求的摘要，并在服务器端强制单次使用，而不是指望客户端守规矩。

MCP 有多个表面会要求客户端、服务器或授权服务器获取他人提供的 URL。若盲目跟随，每一处都可能导致服务端请求伪造：授权服务器获取 Client ID Metadata Document、客户端跟随 `WWW-Authenticate` 质询中的 `resource_metadata` URL，或验证器解析工具 `inputSchema` 里的 `$ref`。规则始终相同：默认绝不自动解引用网络 URI。即使确有必要，也必须作为显式选择加入的操作，置于允许列表之后，阻止私有和链路本地地址、强制 HTTPS，并设置超时。因为 URL 在验证时看似普通，真正请求时却可能解析到内部地址。DNS 重绑定就是同一间隙在本地 HTTP 服务器上的体现：主机名第一次解析到安全地址，下一次查询却指向回环或内部地址。因此，第 19 课的 Origin 验证与 localhost 绑定正是为封堵它而设。图标也以图片形式带来规模较小的同类风险：只接受 `https:` 或 `data:` URI，要求与声明图标的服务器同源，并把 SVG 当作可执行内容而非普通图片，因为 SVG 可以携带脚本。

供应链风险在上述环节之前就已出现。注册表条目、软件包版本和实际响应请求的端点，是来自三个不同权威方的三项独立事实。把注册表命中当作自动信任，就混淆了三者。命名空间必须通过已认证所有者验证，不能只做字符串匹配，因为单纯前缀检查既会接受真实命名空间，也会接受仿冒名称。软件包或远程来源必须按摘要固定，因为浮动版本标签明天可能指向与审核时不同的字节。准入后仍要重新观察运行中的服务器，因为已通过审核的服务器以后仍可能新增工具——这只是换了名字的供应链 rug pull。这些检查彼此不可替代。

策略引擎拒绝请求时只有三种可用通道，选错通道本身也是常见错误。请求格式有误，例如点名服务器从未注册的工具，属于 JSON-RPC 协议错误：错误码 `-32602`，与第 02 课处理未知工具时相同。模型需要读取并可能据此调整的拒绝，例如触发速率限制或工具因 rug pull 被暂扣，应放进带 `isError: true` 和说明内容的正常结果，不能使用 JSON-RPC 错误，更不能虚构错误码。人们很容易选用 `-32001` 一类代码，因为旧式 `-32000` 到 `-32019` 区段看起来像可供自定义拒绝的空间。事实并非如此：该区段只供旧实现使用；`-32020` 到 `-32099` 留给规范本身；如果确实需要应用自定义代码，必须放在 `-32768` 到 `-32000` 范围之外。多数策略拒绝根本不需要自定义代码，因为 `isError` 已提供模型可以读取、向用户解释、有时还能据此修正的通道。

这些控制都无需人在环路中，这正是它们的意义。一个自动步骤若同时读取不可信输入、接触敏感数据并执行后果重大的动作，就形成了清单中每种威胁都想抵达的局面。拆分这一步，才能避免一次漏审演变为事故：先固定描述符，让后续静默变更显形；描述进入模型前先扫描；凭据离开服务器前验证其受众；网络引用被获取前先拒绝。速率限制、超时，以及用低权限沙箱进程运行工具处理器则更加朴素。它们不理解攻击长什么样，这恰恰是价值所在：即使上游所有更聪明的检查都漏掉问题，它们仍能限制损害范围。

## 交互实验

图中有八种威胁围绕中央网关节点：顶部附近是描述投毒和 rug pull；右侧是工具遮蔽与 token 透传；底部是 `requestState` 篡改和网络 `$ref`；左侧是 DNS 重绑定与供应链漂移。图中没有任何罕见机制。每条辐射线都是同一思路的变体：服务器、注册表或客户端提供了某些内容，网关选择验证而非轻信。中央列出了应对全部八类威胁的三个动作：固定描述符，让后续变更可见；描述进入模型前先扫描；限制单个调用方或工具的能力，即使每次调用单看都合规。

## 实践实验

打开 `code/main.py`。它构建了一个 `RiskGateway`，前接 `search_helpdesk` 和 `sync_upstream_ticket` 两个工具，随后注册第三个工具——其 schema 引用了网络 `$ref`——以及第四个工具——其描述携带注入指令。

```bash
python3 code/main.py
```

对照核心概念阅读打印出的交互记录。`bulk_import` 的注册行显示 `accepted=False`：网络 `$ref` 让它在进入工具目录之前就被拒绝。`draft_reply_wizard` 的注册行显示 `accepted=True`，原因中列出命中的可疑短语：被投毒的工具仍会留下记录，但会当场隔离。请求日志中，第一次 `search_helpdesk` 调用成功；随后 `gateway.observe()` 用变化后的 schema 模拟描述符刷新；即使工具名完全没变，紧接着对同一工具的调用也会返回 `isError: true`，并因 rug pull 暂扣复审。`gateway.approve()` 解除暂扣并重新固定哈希，后续调用再次成功。观察 `sync_upstream_ticket` 的两次调用：第一次把 `upstream_credential` 设为客户端认证所用的同一 token，因 token 透传被拒；第二次使用不同的、限定给上游的凭据，调用成功。最后几次 `search_helpdesk` 调用会超过设为四次的 `rate_limit`，本应成为第五次的调用返回执行错误，而不是静默排队或崩溃。然后向 `SUSPICIOUS_PHRASES` 添加一个短语，注册描述中包含该短语的新工具，确认它注册时便立即被隔离，无需等到有人调用。

## 关键术语

| 术语 | 含义 |
|------|---------|
| 元数据投毒 | 在工具名称、描述或注解中嵌入与工具实际功能无关的指令 |
| Rug pull | 更改此前获批的工具描述符，通常保持工具名称不变 |
| 定义固定 | 批准时对完整工具描述符计算哈希，以便检测后续变化 |
| 工具遮蔽 | 两台服务器暴露相同的非限定工具名，导致发现顺序静默选中其中之一 |
| 混淆代理 | 中间方受骗，替攻击者使用自身受委托的权限 |
| Token 透传 | 把客户端限定给 MCP 服务器的 bearer token 转发给无关的上游 API |
| `requestState` 篡改 | 修改本应由客户端原样返回的不透明 MRTR 状态 |
| SSRF | 服务端请求伪造：诱使服务器获取内部或非预期 URL |
| DNS 重绑定 | 主机名在验证时解析到安全地址，发起请求时却解析到内部地址 |
| 供应链漂移 | 注册表条目、软件包或运行端点在准入后各自独立变化 |
