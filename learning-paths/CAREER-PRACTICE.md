# 职业实践：一个项目，四大领域

用一个项目展示技术深度、agent 辅助交付、产品决策和发布后的责任承担。选择一个职业方向，让同一个用户问题贯穿该方向的专项课程与四大核心领域。

这是独立的实践指南。作品集记录的是你能展示的能力；完成它并不代表你具备职业经验，也不保证获得工作。

## 检查起点

如果你是初学者，先从[软件工程基础](https://aieng-zh.cn/learning-paths.html#software-fundamentals)开始，完成各课列出的前置要求。职业路线是专项补充，不能替代底层课程。

如果你已有同等知识，跳过基础课之前，先在一个小仓库中展示它：

- 配置干净的环境，做一次有版本记录的修改，并用测试复现一个失败。
- 解释一个小应用的请求、数据和错误边界。
- 把凭据留在源码之外，限定权限，并从失败请求中恢复。
- 运行一个面向模型的功能，解释它的评估、回退、延迟与成本。

无法解释或复现结果时，回到对应的基础课。然后检查所选职业指南的基础要求，例如评估工作需要的统计学，或 AI 数据系统需要的数据流水线。

## 按顺序学习，始终围绕同一个项目

1. 打牢[软件基础](https://aieng-zh.cn/learning-paths.html#software-fundamentals)。保留可复现的仓库，其中至少有一个经过测试的端到端行为。
2. 在构建功能前开始[产品判断与交付](shaping-the-build.json)。观察工作流，明确用户成果，记录假设，并选择最小的有效实验。
3. 将 [AI 应用基础](building-and-deploying-ai-applications.json)用于这个实验。只构建该切片实际需要的界面、来源依据、评估、失败处理和运行边界。
4. 实施时使用 [Agent 辅助工程](using-coding-agents.json)。界定有边界的任务，提供上下文，控制工具，审查修改，并独立验证正在运行的产物。
5. 沿着你的[专项路线](https://aieng-zh.cn/learning-paths.html#career-chooser)深化同一系统。只有当该角色所需的证据要求复杂度时，才增加复杂度。
6. 闭合产品循环：收集反馈，向利益相关方简报，完成一次责任明确的改进，并重跑相关评估和成本比较。

遵循每条路线列出的课程顺序和前置要求。共享课程只需要一个在本项目中用好的产物，不需要重复的完成记录。引导课程的预计分钟数不包括独立项目与审查时间。

工作台路径要求先学习 [Agent 循环](../phases/14-agent-engineering/01-the-agent-loop/docs/zh.md)和 [Agent 系统的失败模式](../phases/14-agent-engineering/26-failure-modes-agentic/docs/zh.md)。其中[持久反馈课程](../phases/14-agent-engineering/46-turn-feedback-into-system/docs/zh.md)也是产品路径最后一节反馈责任课程的前置课。

## 选择一个职业项目

下面是可选项目，不是六份作业。收窄范围，直到你能运行完整工作流，并解释每个边界。

| 职业方向 | 一个连贯的项目 | 项目必须展示的证据 |
|---|---|---|
| 客户 AI 部署 | 为支持请求提出分类，并将不确定案例交给人工的受理助手。 | 实际观察的受理流程、人工基线、批准边界、试点决策，以及根据反馈修改的交接。 |
| 开发者体验与教育 | 带快速入门和失败示例、可运行的有来源依据回答 API 集成套件。 | 干净机器上的配置、另一位开发者的试用过程、复现的阻碍，以及任务完成情况的可测改进。 |
| AI 数据系统 | 有版本记录的政策文档摄取与检索流水线。 | 数据血缘、时效性和删除检查、检索评估、摄取失败演练，以及修正的数据质量控制。 |
| Agent 系统工程 | 在可丢弃工作区中提出有边界修改的仓库维护 agent。 | 工具权限、上下文与状态轨迹、被拒绝的越界操作、终止、恢复，以及独立补丁审查。 |
| LLM 产品工程 | 带引用、结构化输出、审查与回退的支持回答功能。 | 来源依据失败、用户验收、延迟、每个成功任务的成本，以及有理由的发布或停止决策。 |
| AI 评估与可靠性 | 有来源依据回答服务的发布门禁和故障演练。 | 有版本记录的案例、针对已知失败的评分器检查、轨迹、回滚证据，以及由事故产生的回归案例。 |

无论选择哪项，都要用 coding agent 执行一个有边界的仓库任务，记录你如何指导和验证它。仅仅构建 agent 产品，并不能展示这种实践。

## 保留证据包

把这些产物保存在自己的项目仓库中。每个测量结果都要注明背后的提交、环境、输入和命令，让审查者能够复现。

| 产物 | 何时可供审查 | 何时需要重做 |
|---|---|---|
| 工作流与决策简报 | 明确用户、当前工作流、期望成果、基线、约束、风险最高的假设和所选切片。 | 目标只是功能清单，或从未考虑更便宜的人工或确定性方案。 |
| Agent 任务与控制 | 明确范围、验收、上下文来源、允许工具、批准点、时间或成本预算、停止规则和交接。 | 权限靠暗示、上下文过时，或 agent 能修改无关资源。 |
| 独立验证记录 | 你检查差异，并用正常、失败和边界案例运行构建后的产物。 | 唯一证据是 agent 报告、生成的截图，或从未触及实际行为的测试。 |
| 检查有效性记录 | 一个刻意引入的行为缺陷使检查失败，修复版则通过。 | 存在缺陷时检查仍通过，或只断言文件、字段存在。 |
| 成果与成本报告 | 基线与候选版使用相同案例、验收标准和核算窗口；失败与重试仍计入总数。 | 把更快的演示当作用户价值，或排除人工审查和失败尝试。 |
| 利益相关方决策说明 | 用清楚的语言说明证据、权衡、建议、未解决风险，以及需要做出的决策。 | 只汇报活动，不说明下一步该怎么做。 |
| 反馈与事故记录 | 一个信号有责任人、修复、复跑证据，以及复审或退役条件。 | 修复未经测试、原失败仍复发，或下一步无人负责。 |

使用 [agent 工作台综合项目](../phases/14-agent-engineering/42-agent-workbench-capstone/docs/zh.md)打包可复用指令、配置、状态、验证与交接。按你的项目权限和失败模式调整。

差异审查也要检查安全、依赖、数据处理和可维护性。接受生成代码的责任仍在你；另一个模型的批准只能作为补充证据。

刻意引入缺陷时，使用可丢弃分支或 fixture。例如绕过引用检查，确认没有依据的回答无法通过验收。记录成功之前，恢复行为并重跑。

## 测量每个成功成果的成本

运行前先定义成功。API 请求完成，不一定代表用户任务完成。

```text
cost per successful outcome =
  (model + infrastructure + tool charges + human review cost)
  / independently accepted outcomes

human review cost = review hours × declared hourly rate
```

一个示例练习：尝试 100 个任务，得到 80 个通过验收的成果。模型与基础设施花费 $12；按假设每小时 $20 计算，两小时审查成本为 $40。总成本 $52，因此每个成功成果的成本为 $0.65，成功率为 80%。

计入全部 100 次尝试、重试与审查的成本。明确每小时费率是假设。实际审查时间与估算的劳动成本分开记录；如果发生工具费用，也应计入。

用相同任务集和成功定义比较基线。一起报告成功率、延迟、审查投入与成本；较低成本可能掩盖更多失败。没有任何通过验收的成果时，报告比值未定义，并调查失败。

如需深入学习，使用可选的 [LLM FinOps](../phases/17-infrastructure-and-production/27-finops-llms/docs/zh.md)课程。它的时间不计入核心产品路径的估算。

## 做一次两分钟利益相关方简报

使用录制或现场审查。请同伴不读你的实现，复述这个决策。

| 时间 | 说什么、展示什么 |
|---|---|
| 0:00 到 0:25 | 谁遇到了问题、当前工作流的成本，以及你测试的成果。 |
| 0:25 到 0:55 | 最小修改和一个有代表性的结果，包括一次失败。 |
| 0:55 到 1:25 | 基线与候选版的质量、延迟、审查投入、成本，以及主要权衡。 |
| 1:25 到 2:00 | 你的建议、未解决风险、下一位责任人，以及继续、调整或停止所需的决策。 |

保留技术细节以便回答问题。记录一条反对意见或分歧，解释它是否改变了计划，以及为什么。

## 进行第二轮迭代

请目标用户在尽量少的指导下尝试任务。记录他们在哪里犹豫、纠正结果、放弃流程或需要交接。面向开发者的项目，应让不熟悉配置的开发者使用干净环境。

选择一个反馈信号和一次安全的故障演练。可以是过时文档、不可用依赖、被拒绝的权限或格式错误的输出。记录检测、控制影响、恢复，以及未解决的部分。

使用[反馈责任](../phases/14-agent-engineering/54-build-the-feedback-ratchet/docs/zh.md)，把最小的有效修复分配给上下文、评估、政策、运行时或待办列表。独立项目中，你可以自己负责；明确下一步和复审日期。

将失败加入相关检查，重跑原案例和新案例，比较成果与成本。不要隐藏回归。简化或停止功能，也可能是合理结论。

## 如实展示证据

把每个结果标为真实用户观察、同伴试用、合成案例或模拟事故。如果无法接触目标用户，记录假设，用同伴模拟测试机制；不要称之为已验证的需求。

区分本地测试、托管试用和生产证据。记录样本量、数据局限、环境和估算成本。不要把单人模拟说成真实流量、客户采用、团队领导或运营经验。

最终演示应复现一个成功任务、一个被拒绝或失败的任务、两轮迭代之间的改进，以及下一项决策背后的理由。
