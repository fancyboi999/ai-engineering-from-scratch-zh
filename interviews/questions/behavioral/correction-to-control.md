这个月里，你已经是第三次提醒代码 agent 在功能变更时不要修改项目的 README 了。每次它都会道歉并修复当前运行。告诉我你现在该怎么做，以及为什么单纯优化 prompt 并不是解决之道。

## Short answer

留在对话里的纠正只能修复单次运行。我将这种重复发生视为工作系统的证据：说明范围边界不具备可执行性。我找出表象背后的原因，并在能够阻断复发的最早层级设置控制措施，此处应当使用范围或权限策略，而非在指令中再增加一段文字。该控制措施必须明确负责人、验证方式以及复审或退役日期。

## Full answer

### 区分原因与表象

“agent 修改了 README”只是表象。其根本原因可能是以下任一种：

- 任务允许写入仓库根目录；
- 文档默认被视为安全可写；
- 任务计划将实现与文档打包在同一个条目中；
- 两个工作单元的所有权存在重叠。

每种原因归属于不同的控制措施。如果制定的规则只是复述表象，在下一个稍有差异的场景中依然会失效。

### 提升至最早生效的层级

| 重复出现的失败 | 长期生效的控制形式 |
|---|---|
| 错误结果或回归 | 测试或评估 |
| 越界或不安全的操作 | 范围或权限策略 |
| 重复出现的设置或命令错误 | 自动化或工具 |
| 重复出现的输出格式错误 | 规范示例配合校验器 |
| 模棱两可的本地约定 | 附带场景检查的指令 |
| 产品决策分歧 | 人工决策记录 |

越早的控制成本越低。使写入无法执行的权限控制，强于事后捕获的审查意见；针对性测试强于要求 agent 记住的一段说明。

### 记录内容

针对每一项被升级固化的纠正，我都会记录表象、根本原因、后果、复发次数、所选控制措施、该控制的验证方式、负责人以及复审或退役日期。并非所有一次性的个人偏好都需要升级固化。只有复发频率或后果严重程度足够高时，才值得引入永久的系统复杂度。

### 为什么不是更好的 prompt

prompt 之前已经清晰说明过三次。问题在于边界依赖于 agent 自行阅读和记忆。拒绝写入的策略不依赖记忆。

## Follow-ups

- **Level 2:** 两条纠正意见措辞不同，但根因相同，如何避免它们变成两条重复规则？ Expected: 将其归一化为根因的稳定指纹，合并为单一控制措施，同时避免将无关失败混为一谈。
- **Level 2:** 初次失败删除了客户数据，是否需要等待其复发？ Expected: 不需要；后果加权允许对严重的初次事故立即升级建立控制。
- **Level 3:** 你会在什么情况下移除已添加的控制措施？ Expected: 系统架构发生变更、有更强的可执行控制取代了它、在合理的观察周期内未再复发，或该控制阻碍的正常工作超过了其防范的风险。
- **Level 3:** 你的精简目标是什么？ Expected: 保留历经磨炼沉淀下来的判断的最小控制集，而不是写出最长的指令文件。

## Wrong answers

- "在指令最顶端用全大写字母添加该规则。" 指令此前早已存在；更醒目的副本依然依赖 agent 能否阅读。
- "升级沉淀每一条纠正意见，以免遗漏任何内容。" 控制规则会不断累积、产生冲突并使上下文臃肿；升级控制必须满足复发频率或后果严重性的门槛。
- "这是 agent 本身的问题，换个模型就好了。" 边界本身不具备可执行约束；更换模型同样会遇到相同的控制缺失问题。
