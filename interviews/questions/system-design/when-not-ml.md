一位产品负责人要求你的团队构建一个模型来决定哪些客服工单应该升级排查。在动手设计之前，哪些关键问题能决定这到底需不需要通过数据学习的模型？又有哪些因素会促使你决定用规则来替代模型？

## Short answer

我首先会探查：简短的规则是否已经能达成业务目标、真实标签是否存在或能够低成本采集、是否有人会根据预测采取行动、决策时刻的数据是否包含有效信号，以及业务上是否容许出现单次错误。当几条判断条件就能保持准确且具备自解释性、缺乏数据标签，或者构建与运维系统的成本超过了更优决策带来的业务价值时，模型方案就该被否决。只有当规则变得过于冗长脆弱时，模型才显现出优势，因为重新训练一个模型远比重写一套复杂的启发式规则更容易维护。

## Full answer

### 反对引入机器学习模型的场景

| 业务前提条件 | 为什么纯规则方案胜出 |
|---|---|
| 业务逻辑仅需几条判断条件且长期保持准确 | 运行成本更低，更容易测试和解释 |
| 缺乏真实标签且无实际可行的采集手段 | 没有用于监督学习的数据源 |
| 没有任何人会依据预测结果采取实际行动 | 更精准的预测得分无法改变任何现状 |
| 决策时刻可获取的数据中不包含有效信号 | 模型无法基于缺失的信息做出判断 |
| 业务上绝不容忍单次错误且无人审核输出 | 概率统计系统不可避免地会出现偶发失误 |
| 系统的研发与运维开销超过了优化决策带来的收益 | 投入产出比为负 |
| 业务模式演变的速度快于模型重训周期 | 生产模型将永远处于过时失效状态 |

一个静态映射表或一个能覆盖 99% 场景的数值阈值就是正确的系统，增加模型只会提高维护成本而收效甚微。

### 支持引入机器学习模型的场景

设计课程引用的规则指南明确指出：不要害怕在没有机器学习的情况下上线系统；但同时也强调，相较于复杂的启发式规则，应优先选用模型。拐点出现在：规则的分支过多、在新场景下频频断裂，且团队已经没有人能完全说清它为何做出某项决策。对于训练模型只需重新喂入数据重训，而对于冗长复杂的规则只能推倒重写。

### 针对工单升级案例的处理步骤

1. 明确工单升级的具体决策是什么、由谁执行，以及决策所需的特征在何时客观存在。
2. 将客服团队当前使用的经验规则梳理出来（哪怕它只存在于 Excel 表格中），并在真实数据上度量其效果。
3. 在开展任何模型训练之前，预先设定好模型必须超越该规则的最低性能提升幅度。
4. 唯有在此之后才去收集数据标签并训练模型，并用完全相同的指标对照规则基线严格评估。

此外，在模型服务突发故障时，该规则本身就是最安全的降级兜底方案，因此无论如何都必须最先构建。

## Follow-ups

- **Level 1:** 工单升级的真实标签从何而来？其延迟有多大？ Expected: 来自历史上的实际升级决策或工单最终处理结果，通常在工单关闭后产生；该延迟直接决定了训练数据所能达到的最新时效。
- **Level 2:** 团队目前完全没有历史工单升级记录，你首先构建什么？ Expected: 首先构建规则引擎，并记录每笔决策及其输入特征，从而启动标签数据的原始积累。
- **Level 2:** 监管机构要求每笔工单升级决策必须具备完全可解释性，系统作何改变？ Expected: 要么坚决保留规则方案，要么将模型严格限制在可解释的形式内，例如浅层决策树或线性模型。

## Wrong answers

- "只要有足够的数据，模型永远能击败规则。" 当特征本身携带的信号极弱时，规则完全可能胜出，超额收益必须实测而非盲目假设。
- "先上线模型，后续再慢慢收集数据。" 没有标签就没有可供训练的数据，更没有任何客观评估模型好坏的基准。
- "启发式基线仅仅是一个初步合理性检查。" 它是真实的业务竞争对手，也是系统故障时不可或缺的安全兜底。
