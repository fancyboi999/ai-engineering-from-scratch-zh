# 编写手册

手册深入解释协议、文件格式或运行时等主题的一个精确版本。课程讲完概念就继续，手册要让读者能预测未展示场景下的系统行为。

本技能包括研究、来源排序、冲突登记、离线运行记录、固定章节结构、写作限制，以及必须输出 TOTAL 0 的审计。适用于任意仓库。课程仓库已有工具，manuals/a2a-101/ 是完整示例。

## 适用情况

- 读者需要预测某系统固定版本在未展示场景下的行为。
- 主题有可固定到提交的规范、schema 或源码树。
- 能离线运行主题或忠实替代实现，记录请求与响应。
- 产物为 60 至 100 页，包含图表，且后续由其他人维护。

## 使用其他方式的情况

- 注意力或检索等通用概念：写课程。
- 无版本可固定，或每周变化：先明确稳定范围。
- 无法运行且无法记录输出：只能交付文章，不能声称有运行记录的手册。
- 简短操作指南或不足约十五节：无需这套完整结构。

## 入门手册规模

| 项目 | 目标 |
|---|---|
| 页数 | 60 至 100 |
| 篇数 | 6 至 8，加一篇参考 |
| 节数 | 约 25 |
| 图数 | 30 至 40 |
| manual.json 学习成果 | 至少 3 |
| 每节要点 | 恰好一个块，至少两项 |

完整示例有七篇、二十八节、七个参考节、三十一张图。

## 方法

1. **固定主题。**记录版本、来源 URL、提交、发布日期、核验日期。
2. **来源排序。**按 schema/proto、规范、项目文档、参考 SDK、运行记录排序。
3. **按许可归档。**原样复制允许引用的来源到 research/sources/，旁边保留许可文件。
4. **事实简报。**在 research/ 按章节和行号索引将使用的每条规则，见 [研究与来源](references/research-and-sources.md)。
5. **冲突登记。**发现来源分歧即分配 D1、D2 等 ID。
6. **构建记录工具。**离线运行并把确定性文件写到 capture/out/，见 [运行记录](references/capture-kit.md)。
7. **按规范规划目录。**每节以规范中可查的一项命名。
8. **编写 manual.json。**填写版本、成果、配色、来源、引文来源、运行命令、篇章，见 [声明文件](references/manual-json.md)。
9. **前言。**标题为“如何阅读本手册”，按下文顺序写。
10. **逐节编写。**遵循固定结构，所有 listing 都从运行记录截取。
11. **按记录绘图。**遵守下方要求与 blueprint-figure。
12. **补齐未测实验。**将每句“未测试”变成真实运行记录，并编写带示例程序的构建篇，见“首审前验证”。
13. **按渲染图像审视图表。**逐张看渲染图，修复后重新看，见“按渲染图像评审图表”。
14. **构建与审计。**修复全部问题，直到 TOTAL 0，见 [审计](references/audit.md)。
15. **执行两次独立审计。**一次对照录制核对数值与一致性，一次对照固定版本源码核对代码断言。
16. **按判断拆分提交。**一节连同图表和新增运行记录是合适粒度；已授权批量同步时可按可审查逻辑批次提交。

## 按规范规划目录

先用规范中的名称建目录，再决定每篇证明什么。

- 前言：front.md，标题“如何阅读本手册”。
- 第一篇：用两节说明主题标准化什么，以及一次完整运行交互。
- 中间各篇：每层一篇，例如发现、数据模型、操作、绑定、安全、扩展。
- 最后实现篇：构建客户端和服务端，用官方一致性工具测试，并解释从上一版本迁移。
- 参考篇：方法表、对象、状态、错误、术语、来源、冲突、图索引。

每节以规范中的对象、操作、绑定、头、错误或扩展命名。“CancelTask 与终止状态”具体可查，“状态机”过于泛化。通用概念放在拥有该概念的对象章节中。

## 前言

front.md 按顺序包含：

1. 读者是谁，读完能做什么。
2. 编写方法和来源权威排序表。
3. 运行记录工具。
4. 引文、示例截取、ID 缩写约定。
5. 可离线执行的首次运行。
6. 篇章顺序，以空 parts 块声明。
7. 图表颜色，以空 palette 块声明。
8. 图 0.1，解释本手册箭头与颜色语法。

## 章节结构

每节顺序如下。参考节和前言有中心论点、来源行，但不需要成果句或 takeaways。

1. 首行一个 # 标题，使用规范术语。
2. 标题下直接放 > 中心论点，一句，英文最多 30 词。
3. 开头从读者经历过的具体场景切入。
4. 前两段内包含“读完本节，你可以……”成果句。
5. 正文由二级标题、以粗体术语开头的定义、图、示例、规则、表格构成。
6. 恰好一个 takeaways 块，至少两个行动项。
7. 最后段以 Sources: 开头，列出编写时使用的全部文件。

完整模板见 [章节模板](references/section-template.md)。

## 围栏类型

| 围栏 | 内容 | 必需字段 |
|---|---|---|
| figure | 按 ID 引入一图 | id、kind、title、claim、caption |
| listing | 从一个记录文件截取 | title、source、lang，可选 note，随后分隔线与原始行 |
| rule | 逐字核对的引文 | label、source，随后分隔线与引文 |
| takeaways | 章节行动项 | 至少两行 - 项目 |
| parts、palette、figure-index、contents | 自动生成的表格 | 空块 |

其他围栏必须有语言。json、jsonl、http、sse 内容必须改为带来源的 listing。

## Markdown 子集

仅使用以下结构，让各版本一致渲染：

- 第一行一个 # 标题，下方中心论点引用。
- 二级、三级标题，可带 {#anchor}。
- 段落与单层无序、有序列表。
- 带表头的管道表格。
- 粗体、斜体、行内代码。
- 引文 `{{key ref}}`、交叉链接 `[text](#s-5-3)`、仓库链接。

原始 HTML、水平分隔线、嵌套列表、四级标题、其他引用块会使构建失败。节锚点为 s- 加将点换成连字符的 ID，例如 s-1-4、s-r-2。

## 示例记录

- 每个 listing 从 capture/out/ 截取，不凭记忆写请求或响应。
- 每行必须逐字存在于来源。
- 用单独一行或行内的 … 标记截取。
- note 说明省略了什么。
- source 给出源文件，供读者查看完整记录。

## 在线系统录制

集群运行时等主题无法在 CI 离线运行，可在自有机器上录制并将证据留在仓库中。

- 将原始录制放在 `capture/lab/<experiment>/`，每个实验一个目录，附上录制脚本。
- 用 `capture/run.py` 从原始文件计算所有图表与正文引用的数值，在 `capture/lab/summary/` 为每组数据写出一个汇总文件。
- 汇总文件保留每次运行，不只存中位数，以便图表绘制分布。
- `capture.check` 重建汇总并与已提交文件比对；录制本身打印一行带原因的 `skipped`。
- 每个实测段落写明机器与样本数，以 `**我们测得**` 开头。
- 不要把不同机器的数值并排比较，须注明机器不同。
- 写明计数的统计窗口，故障期间的计数不同于全程计数。
- 提交前先清除密钥、token、kubeconfig、主机名、公网地址和人名，并在不暴露秘密的前提下记录脱敏位置。
- 每个录制文件保持精简，长日志裁剪为逐行精确的摘录文件。

## 首审前验证

通过静态审计的手册仍可能证据不足，提请审校前完成以下事项：

- 列出所有声明“未测试”的句子，在实验室能跑的逐项补跑并替换为实测结果。
- 最后一篇设为构建篇，编写读者可运行的小程序，各录制一次运行并展示输出。
- 亲手构建主题留给用户完成的部分，例如没有空闲计时器的运行时中的空闲挂起器。
- 提供故障演练脚本，主动触发每类文档化故障并打印现象、状态、修复步骤与耗时。
- 将项目官网的核心宣称与实测结果并列成表，注明哪些得到验证。
- 第二次运行与第一次不一致时同时保留两者，如实说明原因未查明，不挑其中一个。
- 后续运行或原始文件推翻早期结论时，立即修正正文。

## 两次独立审计

请两位未参与撰写的审校人审阅文件，只给文件，不给你的结论。

- **数值与一致性。**每个实测数值与录制一致，且在各节、图表、要点和表格中完全相同；listing 每行都在源文件里；每个实测段落点名正确的机器。
- **代码断言。**每个标志、默认值、计时器、上限、方法、字段、状态、命令和错误字符串都与固定版本源码一致，每条发现注明源文件与行号。
- 应用前先对照原始证据核实审校发现，审校同样可能出错。
- 记录每条发现是采纳、跳过还是部分采纳，并写明理由。

## 来源、引文与冲突

- sources 按权威排序，分歧时遵循较高来源并明确说明。
- 规则逐字引用，后接引用键，例如 `"quoted text" {{spec §3.1.5}}`。
- quoteSources 声明所有引用键，映射归档文件，无法归档时为 null。
- null 来源（如 SDK）只转述，不直接引用。
- 来源分歧时，正文引用双方、说明选择并链接登记项。
- 冲突表放来源参考节，五列为 ID、来源说法、选择、涉及章节、上游状态。
- 引用规范、源码、论文和主题官方文档，不引用其他指南、课程或书籍。

## 写作限制

| 项目 | 英文限制 |
|---|---|
| 句子 | 最多 25 词 |
| 中心论点 | 一句，最多 30 词 |
| 图表断言 | 一句，最多 28 词，以句号结束 |
| 要点 | 祈使句，最多 20 词 |
| 段落 | 最多六句 |

使用第二人称解释机制。术语定义一次，始终一致，并加入术语表。引用、代码、引文标记免检。中文使用这些清晰表达原则，不套用英文分词。

不用分号、英文缩写、长短破折号。英文不用 `may`，改用 `can` 或说明条件。禁用表达见 [写作规则](references/prose-rules.md)。

## 图表要求

使用 blueprint-figure，并满足：

- 十种类型之一：sequence、structure、flow、comparison、timeline、tree、state、decision、layers、chart。
- 实测结果画成读取汇总文件的 `chart`：每次运行画成一个点，加中位数线并直接标注线条。
- 同一组数据只画一张 chart，其他章节链接到它。
- 使用运行记录中的真实 ID、字段、方法与序号。
- 每图一句断言，英文最多 28 词。图注说明读图顺序和记录文件。
- 不用泛化组件框、统计卡、进度条。
- 比较主题两种行为，不与自己的旧版本比较。
- 每手册各色含义固定，rose 失败、grey 主题外、amber 生命周期、teal 持久状态。
- 使用下方八种箭头，图 0.1 说明本手册使用的样式。
- viewBox 宽 640，高最多 760，字至少 11 单位，文件最多 40KB。
- 根有 role=img、title、至少 40 字符 desc。
- 所有 ID 以图 ID 开头，因为图表共用一页。
- 颜色为 var(--m-<token>,#hex)，hex 为 token 浅色值。

| 箭头 | 含义 |
|---|---|
| 墨色实线 | 调用或请求 |
| 墨色虚线 | 响应 |
| 青色实线 | 持久写入 |
| 琥珀虚线 | 状态变化 |
| 梅色实线 | 模型调用或计算 |
| 橄榄虚线 | 系统外部影响 |
| 靛色点线 | 流或事件 |
| 玫红虚线 | 失败 |

## 对象造型与项目标志

封面插图与架构图展示具体对象而非抽象数据，一排相同的方块无法传达结构。

- 用造型表明对象身份：客户端用终端，网关带端口，服务器用塔体，数据库用圆柱，对象存储用桶。
- 用平面表达包含关系：厚底板表示宿主机，地砖表示分组，开放线框表示 pod，带壁壳体表示沙箱。
- 画出关键状态：将已停止或已挂起的工作负载画成实线运行体旁的虚线轮廓。
- 让大小和位置反映职责，把核心事件放在视觉中心。
- 在运行真实项目的组件上放官方项目标志，只从官方矢量素材提取，不凭记忆手绘。
- 标志用单一调色板色投影到所在立面；28 至 40 单位下看不清时省略。
- 在路径数据旁记录每个标志的来源与许可证或商标说明，并在手册来源页声明标志归属。
- 造型与标志只用于封面和架构图；统计图、时间线与决策图保持平面。

课程仓库中，造型位于 `manuals/_shared/forms.js`，标志位于 `manuals/_shared/marks.js`，图表套件通过 `mark` 绘制标志，`manuals/agent-substrate-101/` 是完整示例。

## 按渲染图像评审图表

通过静态检查的图表仍可能难读，要看渲染图像而非源码。

- 按页面宽度与两倍宽度、浅色与深色主题分别渲染每张图并逐张查看。
- 检查读者能否在五秒内看懂唯一结论，不看文字标签能否认出各个对象。
- 修复拥挤、重叠、裁切以及离对象过远的标签，重新渲染再看。
- 普通图表至少迭代三轮，封面至少四轮。
- 对照正文核查图表，图注不得超出录制所能证明的范围。

## 构建与审计

课程仓库根目录运行：

```bash
node --test site/test_manuals.js
node site/build-manuals.js
node manuals/_shared/figkit.js build manuals/<id>
node scripts/audit_manuals.js --manual <id>
```

仓库外按 [审计](references/audit.md) 实现同样检查。修正文字，不放宽限制。TOTAL 0 前不能合并。

审计即将提交的暂存树而非磁盘目录，防止忽略规则漏掉 listing 引用的文件：

```bash
git add manuals/<id>
STAGED=$(mktemp -d)
git checkout-index -a --prefix="$STAGED/" && (cd "$STAGED" && node scripts/audit_manuals.js --manual <id>)
```

首次推送前还需检查：

- 确认 `.gitignore` 保留录制目录下的 `.log` 文件，必要时添加例外规则。
- 在 `cheatsheets/topics.yaml` 将手册加入对应主题，并同步对应速查表的 `sources` 与 `source_hash`。
- 用 `node site/build-manuals.js --drafts` 构建并在静态服务器预览 `site/`。

## 提交规则

- 每节一提交，包含相关图和新增记录。已授权批量同步可按逻辑批次。
- 消息格式 feat(manual/<id>): <section slug>。
- 不提交生成的 site/manual-<id>.html、site/manuals.html、site/manuals-data.js。
- 未完成前 status=draft，ready 手册必须有 README.md。
- 归档来源与 manual.json 的 pin 一起更新。

## 完成前检查

- [ ] manual.json 有效，pin 含 subject、version、source、commit、date、verified。
- [ ] 每节标题对应规范一项。
- [ ] 每节有中心论点、前两段成果句、一个要点块、Sources 行。
- [ ] json/jsonl/http/sse 均为带记录来源的 listing。
- [ ] 离线记录检查无漂移。
- [ ] 至少 24 字符的引用逐字存在于归档文件。
- [ ] 每冲突有 ID，涉及章节链接到它。
- [ ] 所有 SVG 被文档引用，并等于脚本输出。
- [ ] 每张图都按渲染图像审视过，每张统计图都绘制了各次运行样本。
- [ ] 封面与架构图使用表明对象身份的造型及源自官方素材的标志。
- [ ] 实验室可验证的“未测试”表述均已替换为实测结果。
- [ ] 构建篇包含带源码的示例程序及各一次录制运行。
- [ ] 每个实测段落写明机器与样本数，不跨机器混比数值。
- [ ] 完成两次独立审计，每条发现均记录采纳、跳过或部分采纳及理由。
- [ ] 暂存树审计输出 TOTAL 0。
- [ ] 手册已登记到速查表主题，录制文件不含密钥、主机名或公网地址。
- [ ] 提交范围与授权批次一致。
