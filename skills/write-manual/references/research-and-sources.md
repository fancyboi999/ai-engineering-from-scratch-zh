# 研究、来源与冲突登记

每个断言都必须可追溯到已排序的来源。写首节前完成研究，并把记录放在手册旁。

## 1. 固定主题

选择一个已发布版本，在 pin 记录：

| 键 | 示例 |
|---|---|
| subject | A2A protocol |
| version | 1.0.1 |
| source | https:// 开头的仓库 URL |
| commit | 标签提交，至少七字符 |
| date | 发布日期 YYYY-MM-DD |
| verified | 最近核验日期 YYYY-MM-DD |

也读取 main，但记录精确提交。只为标签版缺少的规则引用 main，用独立键（如 spec-main），并标明尚未发布。

## 2. 来源排序

按权威排序。协议常用顺序：

| 等级 | 来源 | 采用内容 |
|---|---|---|
| 1 | 标签版 schema 或 proto | 所有对象、字段、枚举值、方法 |
| 2 | 标签版规范 | 全部行为规则，逐字引用 |
| 3 | 项目官方文档 | 项目对主题的解释，过时处标明 |
| 4 | 固定标签的参考 SDK | 规范未定义处的真实实现 |
| 5 | 运行记录工具 | 手册展示的所有请求、响应、事件 |

分歧时较高来源优先，正文明确说明。前言放同一张表，增加“引用键”列。

## 3. 归档可引用来源

- 只有许可允许时才复制到 research/sources/。
- 原样复制，旁边保留许可文件。
- research/sources/README.md 说明各文件、上游路径、提交。
- 多页合并时，每页前加注释说明原路径。
- 归档文件与 pin 一起更新。

## 4. 写事实简报

完整阅读归档来源。在 research/ 中将每条将使用的事实写为一行，以章节和行号结尾，例如 `[spec §3.1.5, L285]`。每来源一份简报较清晰，例如 brief-spec.md、brief-docs.md。正文引用来源，简报指引审阅者查证位置。

## 5. 引用与标注

- 规则逐字放在直或弯双引号内，后接引文，例如 `"..." {{spec §3.1.5}}`。
- quoteSources 声明所有键，映射归档文件或 null。
- null 表示无法归档的来源，例如 SDK，只转述并引用路径，不直接引用原句。
- 其他 SDK 用独立键和标签，例如 `{{sdk-go a2asrv/agentexec.go at v2.6.0}}`。
- 引用规范、源码、论文与主题官方文档，不引用其他指南、课程或书籍。

## 6. 冲突登记

规范可能与自身、schema、文档或 SDK 冲突。每个分歧只记录一次，涉及章节都链接到它。

按发现顺序分配 D1、D2 等 ID，在来源参考节放表：

| ID | 来源说法 | 手册遵循 | 涉及章节 | 上游 |
|---|---|---|---|---|
| D1 | **订阅方法。**Proto 为 GET，§5.3 和 §11.3.2 为 POST | 遵循 proto，同时接受两者 | 各节链接 | 上游 issue 或 PR 状态 |

来源列先用粗体写两至四词主题，再按章节号陈述双方。选择列写明采用哪方，默认是较高来源，例外要说明理由。

涉及章节完整呈现：

1. 引用第一来源并标注。
2. 引用冲突来源并标注。
3. 说明遵循哪方及原因。
4. 告诉读者怎么做，例如同时接受两者，或取消失败后调用 GetTask。
5. 链接登记项，例如 `[冲突 D1](#s-ref-sources)`。

每版发布前重查所有未解决冲突，在上游列标记未解决、部分修复、main 已修复但未发布、已发布。后续发现用 N1、N2 等新序列，旧 ID 不变。

## 7. 比较实现

规范未定义处，读取各官方 SDK 的一个固定标签并比较。表格每 SDK 一行，每绑定或场景一列。每格引用 SDK 键和文件。记录工具与参考 SDK 不同时，在工具 README 说明选择。

仓库示例：manuals/a2a-101/research/ 保存简报，manuals/a2a-101/sections/r-6-sources.md 登记四十项冲突。
