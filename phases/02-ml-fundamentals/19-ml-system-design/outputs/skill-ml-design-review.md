# ML 系统设计审查（ML Design Review）

当有人分享一份用于指导现实决策的模型的系统设计文档、提案或方案规划时，使用此 Skill。请按以下顺序逐一审查文档，优先汇报阻断性缺失（Blocking Gaps），其次是其他缺失项，最后提出澄清问题。

## 第 1 步：检查六项阻断性必填项

如果缺少以下任意一项，立即暂停审查并要求补充修复：

1. **决策动作（Decision）。** 文档必须明确指出由谁或什么系统依据预测结果做出何种行动决策。
2. **业务指标（Business metric）。** 文档必须指明该决策旨在提升的业务结果指标，以及如何通过对照实验进行量化评估。
3. **强基线（Strong baseline）。** 文档必须将模型与经验规则或现有系统进行比对。仅对比多数类基线属于不合格。
4. **无特征泄露（No leakage）。** 文档必须确认每个特征在做出预测的精确时间点均已真实存在。
5. **发布与回滚（Rollout and rollback）。** 方案必须包含 Shadow（影子）或 Canary（金丝雀）灰度阶段，以及分钟级生效的回滚机制。
6. **故障默认兜底（Failure defaults）。** 必须为每一种系统故障模式指定安全的默认操作，例如回退到经验规则或沿用上一次有效评分。

## 第 2 步：检查问题建模定义

- 预测目标明确声明了实体对象、目标值和预测时间窗口，例如“用户在未来 30 天内注销”。
- 文档阐明了为何简单的业务规则或查表无法满足需求。
- ML 任务类型与业务决策匹配：分类、回归、排序、预测或异常检测。

## 第 3 步：检查指标分层

| 层级 | 审查要点 |
|---|---|
| 离线指标 | 指标是否与实际决策阈值严格对齐？如果系统仅对前 5% 的用户采取行动，必须测量前 5% 的精确率（Precision@top 5%）。 |
| 在线指标 | 哪些线上实时信号能直接反映模型运作正常：建议采纳率、被评分请求占比、分数分布？ |
| 业务指标 | 采用何种实验评估业务产出，预计多久能观测到统计显著的结果？ |
| 护栏指标 | 哪些指标必须确保绝不恶化：成本、延迟、用户投诉量、退订率？ |

## 第 4 步：检查数据与标签

- 标签的真实来源表及该表的数据负责人（Owner）。
- 标签到达延迟（以天为单位），以及在真实标签到来前团队监控什么指标。
- 正样本数量及类别平衡度。
- 按时间切分的留出验证集（Holdout），保留最近一段时间的数据。

## 第 5 步：用算术公式校验推理方案选择

索取五个关键数字：实体总数、每日请求量、峰值 QPS、最大允许数据陈旧度（小时）以及 p99 延迟预算。随后对两种模式测算成本：

```text
批处理每日运行次数 = 24 / (最大陈旧度小时 - 批处理单次运行时长小时)
批处理每日成本     = 实体总数 * 每日运行次数 * 单次预测单价 + 查表请求量 * 查表单价
在线服务所需副本数 = max(2, ceil(峰值 QPS / 单副本承载 QPS))
在线服务每日成本   = 副本数 * 单副本每小时成本 * 24
```

- 当最大允许陈旧度短于一次批处理任务耗时时，批处理在物理上无法满足需求。
- 当模型自身推理延迟超出 p99 延迟预算时，在线推理不可行。
- 当两者皆可行时，优先选择成本更低者，并核算批处理预测中有多少分数未被实际读取。
- 没有历史行为的新实体需要具备在线推理兜底路径或规则处理。

## 第 6 步：检查反馈循环（Feedback Loops）

审查模型的决策是否会污染未来用于训练自身的样本数据：

- 业务干预（如挽留优惠或支付拦截）是否掩盖了真实的自然流失/欺诈结果？
- 是否只有被模型曝光展示的项目才能收集到用户反馈？
- 是否保留了绝对不施加任何干预的随机留出组（Holdout），以收集纯净数据？
- 系统是否在记录每个样本时同步记录了预测分数与最终采取的决策？

## 第 7 步：产出审查报告

使用以下格式输出：

```text
评审结论：可以评审 | 建议修改
阻断性缺失：<缺失项列表，或"无">
待补全项：<非阻断性缺失项列表>
推理模式校验：<批处理 $/天, 在线推理 $/天, 所选模式, 通过或未通过>
澄清问题：<向作者提出的至多 5 个关键问题>
```

若需对 JSON 格式的设计文档自动评分，请在课程目录运行 `python3 code/main.py path/to/design_doc.json`。
