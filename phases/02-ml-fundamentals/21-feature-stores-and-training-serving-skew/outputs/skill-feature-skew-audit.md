# 特征偏斜审计（Feature Skew Audit）

当模型在离线评估中得分极高但在线上表现不佳时，或者团队正在引入特征平台（Feature Store），以及新特征即将上线发布前，使用此 Skill。请严格按顺序推进以下审计步骤，并记录所有审查发现。

## 第 1 步：梳理特征的双轨计算路径

对于每一项特征，明确梳理并写出两条路径：

```text
训练路径：<源数据表> -> <特征转换代码> -> <按标签时间关联 Join>
推理路径：<实时数据源> -> <特征转换代码> -> <特征库或请求时动态计算>
```

如果两条路径引用了不同的转换代码实现，直接标记该特征为“两套独立代码路径（two code paths）”。这是最常见的偏斜风险来源。

## 第 2 步：检查训练集关联是否存在时空穿越（Time Travel）

- 关联逻辑必须使用标签的精确时间戳（Label timestamp），绝不能仅按实体键（Entity key）关联。
- 关联仅保留事件时间戳（Event time）在标签时间戳或之前的历史记录中最新的一条。
- 丢弃距离标签时间超出生存时间（TTL）的过期快照。
- 回填或修正的历史记录必须携带创建时间戳（Created timestamp），且关联必须自动忽略在标签时间之后才写入的数据。
- 滑动聚合窗口必须在标签时间截止。类似“标签时间前后 30 天”的聚合窗口会造成严重的特征穿越泄露。

快速自测法：统计训练集中特征记录时间戳晚于标签时间戳的样本行数，大于 0 即证明存在特征泄露。

## 第 3 步：比对两轨的特征定义

针对每一项特征，在以下维度逐一比对两条计算路径：

| 校验维度 | 审查问题 |
|---|---|
| 时间窗口边界 | 窗口边界是左闭右开还是双闭？两条路径的处理是否一致？ |
| 缺失值默认兜底 | 对于无历史行为的新用户和超出 TTL 的过期数据，两条路径是否采用相同的默认值？ |
| 单位与数据类型 | 是否使用相同的货币单位、相同的时区，以及相同的整数/浮点类型？ |
| 数值舍入精度 | 是否在完全相同的计算步长执行完全相同的舍入规则？ |
| 离散类别映射 | 是否使用统一的词表（Vocabulary），对未知未知值的处理逻辑是否一致？ |

## 第 4 步：比对数据时效性（Freshness）

- 训练数据中的特征值在标签时间点平均已存在多久，最长存在多久？
- 线上推理时读取的特征值在请求到来时平均已存在多久，最长存在多久？
- 当特征物化（Materialization）任务失败时会发生什么？TTL 机制必须将过期旧值降级为默认值，绝不能静默继续提供陈旧数据。

如果模型是在长达一周前的旧特征快照上训练出来的，在面对线上秒级实时的全新数据时表现可能会产生不可预知的变异。尽量对齐时效性，或者直接在具备相同线上时效性的特征切片上重新训练模型。

## 第 5 步：量化偏斜程度

1. 采样记录线上推理路径实际使用的特征值快照，附带实体 ID 与请求发生时间戳。
2. 使用离线训练路径在完全相同的实体和时间戳上重新计算这些特征。
3. 针对每个特征，统计不一致比例（Mismatch rate）以及平均绝对差值（Mean absolute difference）。
4. 通过三组对比拆解偏斜根因：线上读取 vs 离线训练关联；离线重新实时计算 vs 离线训练关联；第二套独立代码 vs 离线实时计算。

当超过 1% 的样本特征存在差异时（除非属于文档明确声明的预期时效性落差），标记该特征存在偏斜风险。

## 第 6 步：输出审计结论报告

```text
特征项：<特征名称, 版本号>
路径架构：统一共享定义 | 两套独立代码路径
时空穿越：未发现 | <受影响样本量与泄漏原因>
定义分歧：<窗口边界、默认兜底值、量纲单位、舍入差异>
数据时效：训练集平均时效 <时长>, 线上推理平均时效 <时长>, TTL <天数>
量化偏斜：<不一致比例, 平均绝对差值>
修复方案：<收敛至单特征中心注册表 | 修正关联 Join 逻辑 | 对齐默认值 | 对齐 TTL>
```

修复优先级：首先彻底根除时空穿越泄露，随后将两条路径收敛为统一的代码定义，最后调谐对齐时效性。
