# LLM 成本优化模式

构建需要控制成本的 LLM 应用时，套用下面这套决策框架。

## 什么时候优化

**以下情况立即优化：**
- 每月 LLM 花费超过 $500，或超过基础设施预算的 10%
- 面向消费者的产品单次查询成本高于 $0.01
- 系统 prompt 超过 1,000 token，且每次请求都会发送
- 超过 30% 的查询是重复或近似重复的
- 日活正在从 100 扩张到 10,000+

**以下情况先别优化：**
- 日活不到 100，还在验证产品市场匹配
- 每月花费低于 $100 且增长缓慢
- 还在迭代 prompt 设计（缓存会把你锁死在某个 prompt 上）

## 缓存策略选择

### 精确缓存

**适用于：** temperature=0、相同 prompt 会重复出现、需要确定性输出。

```python
key = sha256(json.dumps({"model": m, "messages": msgs, "temp": 0}))
```

- 实现：30 分钟
- 命中率：大多数应用 10-25%，FAQ 机器人 40-60%
- 延迟：<1ms（字典查找）
- 风险：底层数据变化后返回过时响应

**不适用于：** temperature > 0、每个查询都独一无二、需要实时数据。

### 语义缓存

**适用于：** 用户用不同措辞问同一个问题、以 FAQ 为主的产品、客服。

- 实现：2-4 小时（embedding + 相似度 + 存储）
- 命中率：在精确缓存之上再多 15-35%
- 延迟：10-50ms（embedding + ANN 搜索）
- 风险：误命中（对相似但不同的问题返回错误的缓存答案）

**阈值参考：**
- 0.98+：非常保守，几乎没有误命中，命中率较低
- 0.95：事实问答的良好平衡点
- 0.90：激进，命中率更高，但有答错风险
- 0.85：只用于低风险应用（建议、自动补全）

**不适用于：** 每个查询都有独特上下文（代码生成）、响应必须反映最新数据、查询空间无边界。

### 供应商 prompt 缓存

**适用于：** 系统 prompt > 1,024 token（OpenAI）或达到各模型的最小长度要求，且同一前缀会反复发送。

| 供应商 | 操作 | 节省 |
|----------|--------|---------|
| Anthropic | 在系统消息上加 `cache_control: {"type": "ephemeral"}` | 缓存前缀省 90%（需先付 25% 的写入溢价） |
| OpenAI | 什么都不用做（自动） | 缓存前缀省 50% |
| Google | 使用 Context Caching API 并显式设置 TTL | 缓存上下文省约 75% |

**不适用于：** 系统 prompt 每次请求都变、prompt 短于最小长度。

## 模型路由规则

### 基于关键词（简单、快）

```
simple:  <= 5 words OR matches FAQ keywords -> gpt-4o-mini ($0.15/$0.60)
medium:  general queries, summaries        -> claude-sonnet ($3/$15)
complex: "analyze", "compare", "debug"     -> gpt-4o ($2.50/$10)
```

- 实现：1 小时
- 准确率：70-80%
- 节省：模型成本的 40-60%

### 基于 embedding（更准）

每个类别嵌入 50-100 条已标注查询。新查询按最近邻分类。

- 实现：4-8 小时
- 准确率：85-92%
- 节省：模型成本的 50-70%
- 额外成本：分类用的 embedding 约 $0.02/1M tokens（可忽略）

### 基于机器学习（生产级）

用历史的查询/模型配对数据训练一个小分类器（逻辑回归或小型 BERT）。

- 实现：1-2 周
- 准确率：90-95%
- 节省：模型成本的 60-75%
- 前提：来自生产流量的标注训练数据

## 限流配置

### 各等级的令牌桶参数

| 等级 | 桶容量 | 补充速率 | 最大 RPM | 每日上限 |
|------|-------------|-------------|---------|-----------|
| Free | 50K tokens | 500/sec | 10 | 50K |
| Pro | 500K tokens | 5K/sec | 60 | 500K |
| Enterprise | 5M tokens | 50K/sec | 300 | 5M |

### 实现清单

1. 多实例应用把桶存在 Redis 里（不要放内存）
2. 用原子操作（MULTI/EXEC）防止竞态
3. 拒绝响应要带 `Retry-After` 头
4. 把被拒请求作为指标跟踪（拒绝率 >5% 说明等级限额太紧）
5. 实现优雅降级：先拒绝昂贵模型的请求，保留便宜模型的访问

## 预算控制

### 三阈值熔断

| 阈值 | 动作 | 可恢复 |
|-----------|--------|------------|
| 月预算的 70% | 记录警告，通过 Slack/PagerDuty 通知团队 | 是（自动） |
| 月预算的 85% | 所有流量路由到最便宜的模型 | 是（自动，下个计费周期） |
| 月预算的 95% | 只返回缓存响应，拒绝新的 LLM 调用 | 是（手动重置或下个周期） |

### 按用户跟踪成本

跟踪每个用户的累计成本。标记超过中位数 10 倍的用户。常见原因：
- 正当的重度用户（给他升级等级）
- prompt 注入循环（机器人在自动发请求）
- 低效的集成（客户端每次出错都重试）

## 成本跟踪字段

每次 API 调用都记录这些字段：

```json
{
  "timestamp": "2026-04-02T10:30:00Z",
  "model": "gpt-4o",
  "input_tokens": 1523,
  "output_tokens": 487,
  "cached_input_tokens": 1024,
  "latency_ms": 1847,
  "cost_usd": 0.006142,
  "user_id": "user_abc123",
  "cache_status": "partial_hit",
  "request_category": "customer_support",
  "complexity_class": "medium",
  "routed_from": "gpt-4o"
}
```

### 看板上的关键指标

- **单次查询成本**（P50、P95、P99）：按模型、按功能、按用户等级
- **缓存命中率**：精确 vs 语义，随时间的趋势
- **模型分布**：各模型的流量占比和成本
- **预算消耗速度**：当前花费 vs 按当前速度预计的月花费
- **拒绝率**：被限流的请求占比，按等级

## 常见错误

| 错误 | 危害 | 修复 |
|---------|-------------|-----|
| temperature > 0 时做缓存 | 输出不确定，过时缓存给出的多样性是错的 | 只缓存 temp=0 的调用，或接受缓存响应失去随机性 |
| 语义缓存阈值太低 | 对表面相似的查询返回错误答案 | 从 0.95 开始，测过误命中率再往下调 |
| 没有缓存失效机制 | 底层数据变化后响应过时 | 设置 TTL（动态数据 1 小时，静态数据 24 小时），数据更新时失效 |
| 所有流量都路由到最便宜的模型 | 质量下降，用户能察觉 | 按复杂度路由，按等级衡量质量，设置最低质量阈值 |
| 没有按用户限额 | 一个滥用用户就能烧光全部预算 | 始终实现按用户配额，哪怕给得很宽松 |
| 忽略输出 token | 每 token 输出成本是输入的 2-5 倍 | 合理设置 max_tokens，使用停止序列，压缩输出 |
| prompt 未稳定就开缓存 | 缓存里塞满旧 prompt 的响应 | prompt 定稿后再开缓存，prompt 改动时清空缓存 |
