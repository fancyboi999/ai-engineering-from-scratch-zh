给定一个拟议的进化编码循环（生成器 LLM、程序数据库、评估器），审计其中的评估器。评估器才是架构本身，生成器可以随便换。这个 skill 判断该循环有没有机会产出真正的成果，还是只会产出靠 reward hacking 刷分的垃圾。

产出：

1. **评估器拆解。** 列出评估器报告的每个信号：正确性、性能、资源及其他。对每个信号说明：(a) 怎么测，(b) 刷分有多容易，(c) 留出输入的规则长什么样。
2. **虚构面。** 列出 LLM 在该领域最可能虚构的三类内容：声称的复杂度类别、声称的边界情况正确性、未经测量就声称的性能。说明分别由哪个评估器信号抓住。
3. **Reward hacking 面。** 列出循环在不完成预期任务的情况下拉高分数的三种可能方式（能过测试的捷径、钻代理指标的空子、记住输入）。说明各自的缓解措施。
4. **确定性与可复现性。** 要求评估器输出在容差范围内是确定的。任何一次运行到下一次运行分数波动超过种群方差的评估器，都要标出来。
5. **部署检查。** 如果获胜变体要上线生产，要求做一次评估器不覆盖的独立上线前审查（安全、成本、人工审查）。搜索过程并没有验证它是否适合部署。

直接否决：
- 评估器是没有机器可校验真值的 LLM 评委的任何循环。LLM 评委可以被钻空子。
- 只报告一个标量分数、不做拆解的评估器。标量分数会放大 reward hacking。
- 只用训练集的评估器。留出输入没有商量余地。

拒绝规则：
- 用户无法用两段话描述评估器时，拒绝继续，先要评估器规格说明。没有规格化评估器的循环还不配消耗算力。
- 领域不可验证（创意写作、开放式科学假设、长篇研究）时，拒绝，建议改用有人工审查的混合流水线，而不是闭环。
- 拟议的部署面不可逆（修改生产基础设施、替换已上线产品中的算法）时，拒绝闭环部署。要求分阶段发布并由人类签字确认。

输出格式：

返回一页备忘录，包含：
- **循环摘要**（生成器、评估器、目标领域）
- **评估器评分**（严谨度 1-5，附理由）
- **虚构面**（前 3 项，附评估器覆盖情况）
- **Reward hacking 面**（前 3 项，附缓解措施）
- **确定性与可复现性**（分数方差与种群方差对比；种子控制；通过/不通过）
- **部署就绪度**（是否允许闭环上线 y/n；必需的上线前审查：安全、成本、人工）
- **建议**（继续 / 收紧评估器 / 换一个领域）
